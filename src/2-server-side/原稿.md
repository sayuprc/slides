# クライアントの知らないサーバーの世界

共有状態と共有実行環境

---

## 導入

今日は、クライアント実装だけ見ていると見えにくいサーバー側の話をします
ゴールは次の 3 つです

- サーバー固有の制約を 2 つの軸で整理できること
- 「正しさ」と「効率」のトレードオフを言葉にできること
- 設計やレビューで見る観点が増えること

深い実装手順を覚える会ではありません
なぜそう考えるかの感覚を持ち帰ってもらうのが目的です

先にお断りしておきます

- 網羅ガイドではありません
- 出てくる具体技術は一例であり、正解のカタログではありません
- 実装手順やベストプラクティス集でもありません

サーバーのすべてを覆う話ではないです
技術の選択はその時々で変わります
パターンを知って、適切な選択ができるようになることが大事です

本題に入ります
サーバーには大きく 2 つの制約があります

1. 共有状態を正しく保つ
2. 共有実行環境を効率よく使う

正しさ側と効率側です
この 2 つはしばしばぶつかります
そのぶつかりどころが、サーバーサイドらしい設計判断になります

そのうえで、両方にまたがるトレードオフと、外部失敗・障害の観測にも触れます
本編の中心は 2 軸です

---

## 1. 共有状態を正しく保つ

まずは共有状態です
一言でいうと、みんなで触るデータを壊さない、という話です

本編で厚く扱うのは Validation、Transaction、冪等性です
競合、状態遷移、外部整合性はその周辺として触れます

### クライアントを信用しない

最初のポイントは、クライアントを信用しないことです

画面で必須入力を弾いても、リクエストは別経路から来ます
hidden の値も改ざんできます
ボタンを連打できない UI でも、同じリクエストは何度でも送れます
ログイン済み画面にいるからといって安全ではありません

UI の制約は利便性であって、セキュリティ境界ではありません
サーバーの入口に来るものは、すべて疑う必要があります

だから Validation はサーバー側で最終判定します
Authentication は「誰か」、Authorization は「何をしてよいか」です
ログイン済みだから通す、では足りません
このユーザーがこのリソースを触ってよいかを、毎回確認します

ここが抜けると IDOR になります
他人の ID を指定しただけでデータが見えてしまう、という抜けです
テナント分離も同じ系統の話で、組織をまたいでデータが見えないかを見ます

アプリの if だけでは守りきれないので、データ設計も防波堤になります
型、NULL の意味、UNIQUE / FK / CHECK、正規化と非正規化です
DB の制約は最後の防波堤だと思ってください

### 同時更新と Transaction

次に、同時に書き込まれると壊れる、という話です

サーバーには同時にアクセスが来ます
ローカルで再現しにくいバグの代表が Race Condition です
典型は「読んでから書く」です

たとえば在庫が 1 のとき:

1. A が在庫を読んで 1 を見る
2. B も在庫を読んで 1 を見る
3. A が在庫を 0 にして保存する
4. B も在庫を 0 にして保存する

結果、在庫 1 なのに 2 件売れます
対策の方向は、DB 制約、行ロック、原子的更新、引当の直列化などいろいろあります
今日いちばん共有したいのは、「同時は起きる」という前提そのものです

複数の更新をまとめて守る道具が Transaction です
たとえば:

1. 在庫を減らす
2. 注文を作る
3. 支払いレコードを作る

途中で失敗したら、全部なかったことにします
1 つだけ成功して残ると、データが嘘になります
Transaction は「まとまり」を約束する道具です

Isolation Level という言葉もあります
どこまで他の処理の途中を見るか、という話です
詳細は今日は深入りしません
名前だけ知っておけば十分です

### 冪等性

次が冪等性です
同じ処理が二度来ても壊れない、という設計です

ネットワークは「届いたか分からない」ことがあります
だから再送は普通に起きます
二重送信も起きます
Retry も起きます

冪等でないと何が起きるか:

1. 決済 API を呼ぶ
2. 応答がタイムアウトする
3. クライアントが再送する

実は 1 回目は成功していた、となると二重課金です
「失敗したように見えた」と「実行されなかった」は別物です
そこで Idempotency Key のような仕組みが出てきます
同じキーなら同じ結果にする、という考え方です

### 状態遷移と外部整合性

周辺の話も少しだけします

状態遷移です
どの状態からどの状態へ遷移できるかを決めていないと、ありえない状態が生まれます
たとえば draft → paid → shipped はよいとして、paid から draft に戻さない、などです
列の値を直接書き換えられる設計だと壊れやすいです
許可された遷移だけを、DB やコードで強制します

外部システムとの整合性も難しいです
DB と外部 API を 1 つの Transaction にはできません
だから部分成功が起きます

典型はこうです:

1. 注文を DB に保存する → 成功
2. 決済 API を呼ぶ → タイムアウト
3. メールを送る → 未実行

このあと再実行したら何が起きるでしょう
決済が実は成功していたら、また二重課金になります
ここで冪等キーや、Outbox / Saga といった話の必要性が見えてきます
今日は名前だけ置いておきます

全部を即座に一致させなくてよいケースもあります
それが結果整合性です
Queue や Event、非同期処理で「遅れても最終的に合えばよい」とする考え方です
強い一貫性が常に正解ではありません
遅れを許容できるなら、設計の自由度は上がります

この章の締めです
「成功したように見える」と「全体として正しい」は違います

## 2. 共有実行環境を効率よく使う

次は共有実行環境です
一言でいうと、サーバーはあなたの専用機ではない、という話です

本編で厚く扱うのは計算量と Memory、DB、非同期、分散です
Connection、並列、Cache、Rate Limit はその周辺として触れます

### 同時に動いている

複数リクエストが同時に動きます
自分の処理だけが動いているわけではありません
CPU、Memory、Connection は共有物です
1 リクエストの浪費は、他の全リクエストの遅延になります

### CPU / Memory / Connection

CPU については、計算量とアルゴリズムです
無駄な計算をしないことが大事です
リクエスト数が増えると、無駄な計算も一緒に増えます
勘で直す前に、まず測って重い場所を特定します

Memory も共有です
1 リクエストで大量に使わない
全件を一度にロードせず、Stream や Chunk で流す
Memory Leak にも注意する
巨大な配列を一度に持つと、他のリクエストのメモリを奪います

Connection は有限です
DB Connection Pool、HTTP Connection、Thread / Process です
特に DB 接続数はすぐ上限に当たります
待たされる接続が増えると、全体が止まります

### DB 負荷

DB はいちばん共有されやすいボトルネックです
アプリが速くても、DB が詰まれば全体が遅いです

見る観点は Query 回数、N+1、Index、Execution Plan です
まずは何回・どのクエリが走っているかを見ます

N+1 のイメージです:

1. 注文一覧を取る → 1 回
2. 各注文のユーザーを取る → N 回

注文が 100 件なら、クエリは 101 回です
ループ内の個別取得は、データ量に比例して悪化します

ついでに、I/O 待ちと CPU 処理は違うという話もします
DB、Network、File を待っている時間は、CPU を使っている時間とは別物です
待っている間も、接続やスレッドなどの資源は占有され得ます
「自分は暇」でも、共有資源は消費しています

並列処理も同じです
独立した処理は並列化できます
ただし並列化すれば必ず速くなるわけではありません
依存がある処理を無理に並べても効果は薄いです
共有資源の上限にもぶつかります

### 非同期処理

全部をリクエスト中にやらなくていい、という話です

ユーザーが待たなくてよい処理は後回しにできます
Queue や Job、バックグラウンド処理です

同期でやりすぎるとこうなります:

- DB 保存
- 画像変換
- 外部 API
- メール送信
- 検索インデックス更新

全部待たせると遅いし、途中失敗にも弱いです

非同期に寄せると:

- 同期では DB 保存だけやる
- 残りは Queue に積む

速さの代わりに、結果整合性と失敗の再処理が必要になります
応答に必要な最小だけ同期にし、残りは非同期へ寄せる判断が重要です

Cache も周辺として触れておきます
計算や DB アクセスを減らせます
ただし無効化と整合性のトレードオフがあります
Cache は速さの道具であり、真実の源泉ではありません
無効化設計がない Cache は負債になりやすいです

### 分散環境

最後に分散です
1 台の成功体験は、複数台で裏切られます

Scale Up は 1 台を強くすること
Scale Out は台数を増やすこと
強くするだけでは限界があります
台数を増やすと、状態の置き場所が問題になります

複数サーバーで動くとき、ローカルメモリに状態を持つと壊れます
典型は Session です

1. Client が Server A にログインする
2. Server A が Session をメモリに保存する
3. 次のリクエストが Server B に行く
4. Server B にはセッションがない

結果、ログインしたのに次の画面で切れたように見えます
Session、一時ファイル、プロセス内 Cache は分散で罠になります
だから Stateless や、外に状態を置く設計、Distributed Lock といった話が出てきます

受けられる量にも上限があります
処理できる以上のリクエストを受けない、というのが Backpressure や Rate Limit です
外部 API にも Rate Limit があります
全部処理しようとして全体停止するより、一部を落とす判断が必要な場面もあります

この章の締めです
共有資源を奪い合う前提で設計します

## 3. 両方にまたがる話

ここが特にサーバーサイドらしいです
正しさと効率は、しばしばぶつかります

Transaction や Lock は整合性を守れます
ただし Lock が長いと性能が落ちます
守りを厚くするほど、待ちが増えます

Cache は高速になります
ただし古いデータを返す可能性があります
鮮度をどこまで許すかが設計です

非同期処理はリクエストを軽くできます
ただし結果整合性を考える必要があります
「今はまだ反映されていない」を扱うことになります

Retry は可用性を上げます
ただし負荷増大と二重実行の危険があります
Retry と冪等性はセットで考えます
落ちている相手に全員が即リトライすると、障害を拡大します

分散は処理能力を上げられます
ただし整合性の維持は難しくなります
台数を増やすほど、状態の置き場と同期が難しくなります

どちらかを捨てる話ではありません
代償を払う場所を選ぶ話です

## 4. 外部は失敗する / 障害を観測する

2 軸の外側にも、サーバーらしい世界があります
ここは本編というより、こういう世界もある、という紹介です

外部システムは信用しすぎない方がよいです
Timeout、Retry、Circuit Breaker、部分障害といった話です
外部 API は自分たちの SLA を保証しません
遅い、落ちる、たまに変なレスポンス、を前提にします

リトライは両刃です
一時障害には有効ですが、相手をさらに追い込むこともあります
冪等でないと二重実行になります
バックオフと上限が必要です
どこまで Retry してよいかは、相手と自分の両方を見ます

ネットワークは壊れます
Latency、Timeout、DNS、接続切断です
リクエストが届いたことと、相手が処理を終えたことは別です
クライアントがブラウザを閉じても、サーバー処理は続き得ます

障害を調査できるようにすることも大事です
Logging、Metrics、Tracing、Request ID、Monitoring / Alert です
起きないことが理想でも、起きたときに追えることが必要です
特に Request ID は、複数サービスを横断する手がかりになります

最低限ほしい観測ポイントとしては:

- リクエストの入口と出口
- 外部呼び出しの成否とレイテンシ
- キューの滞留量
- エラー率の急変
- デプロイとの相関

アラートは、人が起きて対応できる粒度にします

## まとめ

今日見た観点をまとめるとこうです

1. 共有状態を正しく保つ
2. 共有実行環境を効率よく使う
3. 両方のトレードオフを意識する
4. 外部失敗と観測まで含める

持ち帰ってほしいキーワードは次です

- 状態: Validation / Transaction / 冪等性
- 実行: 計算量・Memory / DB / 非同期 / 分散
- 横断: Lock・Cache・Retry の代償
- 別枠: Timeout・Log・Request ID

「動いた」の次に、「壊れ方」を想像してください

レビューのときには、たとえばこう聞けます

- 二重に来たらどうなる？
- 途中で失敗したら何が残る？
- この処理は共有資源をどれだけ使う？
- 別サーバーでも同じ動きか？
- 障害時に追える手がかりはあるか？

最後に、こういう世界もある、という名前だけ置いて終わります
次回やる約束ではありません
今日の地図の周辺にある用語です

- Isolation Level
- Optimistic / Pessimistic Lock
- Transaction Outbox / Saga
- Cache invalidation
- 分散トレーシング

全部覚える必要はありません
「そういう話がある」と知っていれば十分です
